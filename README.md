# Campus Maintenance Service Operations Optimizer

DCIT 204/308 joint semester project — University of Ghana, Legon.

A console-driven Java system for a campus maintenance service: it takes in
requests (broken projector, flooded bathroom, etc.), stores them in a
database, prioritises them by urgency, dispatches the nearest available
worker, and routes them there with Dijkstra's algorithm. Every data structure
and algorithm behind it is built from scratch (no `java.util.HashMap`,
`PriorityQueue`, `Stack`, etc. in the assessed logic) — see
[docs/DSA_Project_Team_Guide.docx](docs/DSA_Project_Team_Guide.docx) for the
full spec, mark scheme, and week-by-week build plan this structure follows.

**This is a console application, not a GUI/web/mobile app** — the examiner
drives every feature from a text menu. The `menu/` package is the only layer
that touches `System.in`/`System.out`; everything else (`structures/`,
`algorithms/`, `db/`, `model/`) is plain Java with no console coupling, so a
GUI can be bolted on later by adding a new front end next to `menu/` without
touching core logic.

    ├── main/java/campus/
    │   ├── Main.java                entry point — boots MainMenu

    │   ├── db/                        DatabaseConnection, SchemaInitializer, CsvLoader

    │   │   ├── linear/                  DynamicArray, LinkedList, Stack, Queue, CircularQueue, Deque
    │   │   ├── priority/                 MinHeap (the dispatch engine)

    │   │   ├── hash/                       HashTable, CustomSet, CustomMap

## What's already here vs. what's a stub

- `pom.xml`, `sql/schema.sql`, `.gitignore`, the CSV headers, and this README
  are ready to use as-is.
- Every `.java` file under `src/` is a **placeholder** — a package
  declaration, a class signature, and a `// TODO` line naming what the class
  is responsible for (taken straight from the spec's use-case table). No
  logic is implemented yet. Test files fail on purpose (`fail("not
  implemented")`) as a reminder to fill them in.
- Fill `data/*.csv` with real Ghanaian campus data first (Week 1 priority per
  the guide) — everything else loads from there via `CsvLoader`.

## Getting started

1. `mvn compile` to check everything builds.
2. Fill in the CSV templates in `data/` (locations, roads, requests,
   resources) with real data.
3. Implement `db/SchemaInitializer` + `db/CsvLoader` to seed SQLite from the
   CSVs — this unblocks everything downstream.
4. Work through `structures/linear/` → `structures/priority/` →
   `algorithms/search/` + `algorithms/sort/` → `structures/graph/` +
   `algorithms/graph/` → `structures/tree/` + `structures/hash/` →
   `algorithms/optimisation/`, wiring each into `menu/` as it's done so the
   console stays runnable at every stage. This order matches
   `docs/DSA_Project_Team_Guide.docx` Section 8 (week-by-week build plan).
5. Log progress weekly in `docs/dev_log.md` and record every meeting in
   `docs/meeting_records/`.

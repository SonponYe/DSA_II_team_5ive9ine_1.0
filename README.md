# Campus Maintenance Service Operations Optimizer

DCIT 204/308 joint semester project — University of Ghana, Legon.

A console-driven Java system for a campus maintenance service: it takes in
requests (broken projector, flooded bathroom, etc.), stores them in a
database, prioritises them by urgency, dispatches the nearest available
worker, and routes them there with Dijkstra's algorithm. Every data structure
and algorithm behind it is built from scratch (no `java.util.HashMap`,
`PriorityQueue`, `Stack`, etc. in the assessed logic) — see
[docs/DSA_Project_Team_Guide.docx](docs/DSA_Project_Team_Guide.docx) for the
full spec, mark scheme, and week-by-week build plan this structure follows.

**This is a console application, not a GUI/web/mobile app** — the examiner
drives every feature from a text menu.

## Read this first: `docs/METHOD_SIGNATURES.md`

That file is the team's binding contract — exact class and method names,
parameters, and return types, split across six groups (G1–G6). Everything
under `src/` is scaffolded to match it exactly. **If you're implementing a
class, open that doc first and build the method to the signature already in
place — don't rename or change it without telling the whole team.**

| Group | Owns |
|-------|------|
| G1 | `Location`, `Road`, `ServiceRequest`, `Resource` (models — done, fields frozen), `DatabaseManager` |
| G2 | `DynamicArray`, `LinkedList`, `Stack`, `Queue`, `CircularQueue`, `Deque` |
| G3 | `PriorityQueue` (min-heap), `HashTable`, `BST`, `BalancedBST`, `BTree`, `CustomSet`, `CustomMap` |
| G4 | `SearchEngine`, `SortEngine` |
| G5 | `Graph`, `DisjointSet` |
| G6 | `GreedyAssignment`, `DPKnapsack`, plus testing & report |

The console menu (`Main` + `*Menu` classes) isn't covered by that doc — it's
shared integration work that calls into all six groups' classes directly.

## What's already here vs. what's a stub

- `pom.xml`, `sql/schema.sql`, the CSV data, `docs/METHOD_SIGNATURES.md`, and
  this README are ready to use as-is.
- `Location.java`, `Road.java`, `ServiceRequest.java`, `Resource.java` are
  **fully implemented** — they're plain data holders with no algorithmic
  logic, so there was nothing to stub. Their fields are frozen per the
  method-signatures doc; don't change them without telling G1.
- Every other `.java` file under `src/main/java/` has the exact method
  signatures from `docs/METHOD_SIGNATURES.md` already typed in, each with a
  body that just throws `UnsupportedOperationException("TODO: implement")` —
  replace the throw with real logic, keep the signature.
- Every `src/test/java/*Test.java` has one `@Test` per public behaviour,
  currently calling `fail("not implemented")` on purpose — fill in normal
  case, boundary case, and invalid input per the project guide's evidence
  checklist (40 tests minimum).

## Getting started

1. `mvn compile` to check everything builds (it does, as scaffolded).
2. G1 implements `DatabaseManager` against `sql/schema.sql`, seeding from
   `data/*.csv` — everything else depends on this being done first.
3. G2 → G3 → G4 → G5 → G6, each filling in their classes from
   `docs/METHOD_SIGNATURES.md`, wiring into the relevant `*Menu` class as they
   go so the console stays runnable at every stage — matches
   `docs/DSA_Project_Team_Guide.docx` Section 8 (week-by-week build plan) and
   the due dates in the "Summary" table at the bottom of
   `docs/METHOD_SIGNATURES.md`.
4. Log progress weekly in `docs/dev_log.md` and record every meeting in
   `docs/meeting_records/`.
